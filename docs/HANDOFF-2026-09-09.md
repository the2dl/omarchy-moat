## The two findings that mattered most

**`cgroup-rate` is evaluated PER CPU, and it was destroying ~88% of a build's
events.** I first tested it unpinned across 32 cores, measured ~130/s per core
against a 1000/s limit, and told Dan throttling was ruled out. That was wrong.
Pinned with `taskset -c 0`: 1,448 events arrived where ~12,000 were expected.
What gets dropped is exec/exit — *ancestry* — which is the input `chain.rs`
correlates on and the source of `process.ns`. It explains both mysteries of the
week: `ns` missing on 80% of rows, and detections correlating at 0.4%.

Raised to `20000,1s`. **Any future test of this must pin a CPU** or it measures
nothing. See `docs/TETRAGON-NOTES.md`, which states exactly what the measurement
does and does not support (it does *not* prove "no loss").

**moat could not see its own event loss.** `PROCESS_THROTTLE` was missing from
the export allowlist, so `moat-x-sensor-throttled` was a rule that could never
fire. "Zero throttle alerts" meant "moat cannot tell whether it is dropping
events".

## The shape of the noise, measured

Use `moatctl feed --json --limit 100000`. **The default limit is 500 and it
silently truncates** — every number I quoted before noticing that was wrong.

- detection-tier rows chain at **0.4%**; signal-tier at **28.8%**.
- 2,027 of 2,105 detection rows are single-process trees with no cross-family
  neighbour (container `pg_isready` health checks, `moat-ship` unlinking its own
  spool). They will never chain, and that is correct.

**This is the open design question.** Dan wants ambiguous single events to be
building blocks that only reach the badge as a sequence. That is right for
families with neighbours (package installs, container work, browser-secret
harvests) and wrong for the ones without. Do **not** gate everything: at today's
rates that switches moat off. The per-rule cross-family neighbour rate over the
full store is the measurement that would decide it, and it has not been taken.

## Enforcement across namespaces — the invariant now

Enforcement stops at the namespace boundary. Kernel policies are split by
`render::split_container_enforcement` (host-scoped deny + a watch-only mirror),
except policies annotated `moat.omarchy/namespace: global` — kernel modules and
BPF programs, which have no namespace to be scoped to.

Userspace has **two predicates, deliberately opposite**, and this is the thing
most likely to be got wrong by a future change:

- `Daemon::may_act_on(&Alert)` — actions. Refuses only on the **sensor's**
  answer. Unknown means actionable. A forged ancestor named `runc` must never
  buy immunity from enforcement.
- `Daemon::may_be_container_path(&Alert)` — readers. Refuses on **any** hint,
  including the spoofable ancestry heuristic. Following a container's path opens
  a host file that merely shares the name; a forged hint should cost a missing
  artefact, not a disclosure.

Two functions rather than one with a flag, so a call site cannot pick the wrong
default by leaving an argument at its zero value.

Note: `in_container` comes from `process.ns.mnt.is_host`, which needs
`--enable-process-ns` (now shipped). **Measured: the sensor has never once
reported `is_host: false`** — every container demotion so far came from the
ancestry fallback. So the sensor path is currently unproven in practice.

## Still open

Ranked as I would take them.

1. **The building-block question above.** Needs the per-rule neighbour-rate
   measurement first.
2. **PID reuse between verification and signalling.** `verify_pid` now refuses
   when it cannot check, and unresolvable targets are spared, but targets are
   still held as numeric PIDs and signalled in a later loop. The real fix is
   `pidfd_send_signal`.
3. **`find_index` conflates parse failure with absence**, so a corrupt
   `baseline.toml` reads as "no block to disable" and the entry is marked
   withdrawn.
4. **`/proc/self/exe` for Spotify** does not establish identity
   (`default.toml`). Narrow or drop it.
5. **No azure-cli entry, on purpose** — its launcher uses `-m azure.cli` and
   `script_arg` returns `None` for `-m`. `az` reading `~/.azure` will alert
   until moat can identify a module the way it identifies a script. Reasoning is
   in `default.toml`; do not "fix" it with another path glob.
6. **`provenance.rs` never verifies file contents.** `%VALIDATION%` records how
   the *package* was validated at install, not whether the bytes still match. A
   trojaned `/usr/bin/curl` classifies as `official`. The per-file sha256 is
   sitting unread in `/var/lib/pacman/local/*/mtree`. Security gap, not noise —
   probably the highest-value untouched item in the repo.
7. **Two tests are dead at HEAD** and were before this work:
   `a_noisy_pattern_is_demoted_exactly_once_and_only_that_pattern` and
   `the_ledger_splits_the_file_into_needs_you_recorded_and_suppressed` — both
   lack `#[test]`.
8. **OPR submission** (`omacom/omarchy-pkgs`, PR adding
   `pkgbuilds/omarchy-moat/`) — deferred until this settles. The plugin
   marketplace is the wrong channel; it ships QML and cannot install a daemon.

## How to work on this

**Every guard must be mutation-checked against PRODUCTION code.** Delete it,
invert it, confirm a test fails. Seven tests written during this work passed
with the guard deleted:

- two asserted `is_err()` where the fixture failed for an unrelated reason —
  assert the *reason*, not the outcome;
- one reimplemented the production filter in its own body, so the mutation
  tested the test (hence `host_targets` and `host_net_members` exist as named
  seams);
- one asserted on `contain.live()`, which is empty in any test because the
  policy load needs a live sensor;
- one lived in `Service.qml`, which `qmltestrunner` cannot instantiate at all;
- one had a one-family chain, so the gate refused before reaching the guard.

Add a **control** to any negative assertion: prove the fixture can produce the
positive case, or the negative proves nothing.

**Do not undo a documented decision without reading why it exists.** This
codebase records incidents in comments. Three times this week a "fix" would have
reintroduced one — the 2026-09-04 AUR miss (demoted steps must still trigger
chains), the `dedupe_key` pid trap, and the quarantine-of-its-own-moatctl case.

**Check claims against the code before acting.** Of the review findings, several
were wrong: `is_interpreter` already covered python/node/perl/ruby; `unacked()`
already excluded suppressed rows; the badge already counted incidents. Three
agents made confident assertions about this repo that did not survive checking.
