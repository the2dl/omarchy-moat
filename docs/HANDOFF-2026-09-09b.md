## What this session's work assumes

**`moat-x-binary-modified` trusts pacman's database.** The mtree is written at
install time and owned by root, so an attacker who can rewrite it can rewrite
`desc` beside it. This raises the bar from "replace a binary" to "replace a
binary and its checksum"; it is not a defence against root.

**The verification cache is keyed on cheap metadata** — path, inode, mtime,
size. A file rewritten in place at the same size with its mtime restored keeps
its key and its cached verdict until the next restart. That evades the cache,
not the check.

**Absence is never a mismatch.** No mtree, no digest for the path, a directory,
a symlink, or a file over the 512MB read cap all mean "no claim". The mutation
that treats any of them as "changed" fails six tests, three in the engine.
Do not change that direction without reading why.

## Reviewing this session's own work found three defects

Written down because all three were in code that had already been
mutation-checked and committed, and none would have been found by running the
tests again.

* **`cmd_kill` opened a pidfd per descendant, all at once.**
  `proc_descendants` is unbounded, a handle is a descriptor, and the results
  were collected with `filter_map` — so past RLIMIT_NOFILE a wide tree would
  have had members survive a kill that reported success. Batched at 64, and an
  unpinnable pid is now reported rather than dropped.
* **`modified_reported` grew for ever.** It is persisted, so a file edited
  repeatedly would grow `state.json` without limit. Capped at 512, oldest out
  first — a bound that can cost a duplicate alert and never a silence.
* **`mtree::entries` trusted the mtree's paths.** `./../../etc/shadow` became
  `/etc/shadow`, so a hostile AUR package could have had the sweep read, hash
  and alert on a file it never owned. Any non-plain component is refused now;
  checked against all 1,124 installed packages and 286,432 entries, none
  rejected.

Also corrected: the sweep's cost comment justified "one package per tick" with
the cost of the WHOLE sweep. What stalls the loop is the worst single package
— 0.191s here — and `tick` runs on the state interval (5s), not per event, so
a full sweep is about 1.6 hours rather than the minutes implied.

## Method notes, because two of them cost real time here

**A guard is not checked until the mutation actually reproduces the bug.**
Twice this session a mutation passed and the guard looked fine:

* reverting the udevadm policy fix left the symlink scan passing, because the
  patch had REPLACED the dead entry rather than adding beside it, so there was
  no symlink left to find. Restored the original from git and re-checked.
* the first pidfd test passed with the pidfd swapped back for `libc::kill`. A
  reaped pid gives ESRCH either way. Only a genuinely recycled pid separates
  them, which needs a PID namespace and `/proc/sys/kernel/ns_last_pid`.

**Measure before building on it.** The mtree work was worth doing because
60,915 of 60,920 files matched. Had that number been 90%, the feature would
have been a noise generator, and nothing in the design would have said so.

**`git stash` plus cargo gives unreliable before/after test counts.** Twice it
served a stale binary and reported identical numbers for different trees. Use
the compiler's own dead-code warnings, or `git show HEAD:<file>`, to establish
what was there before.
